# ADR 0001：以开放问题为中心的探索工作台

日期：2026-10-24。
状态：提议。产品方向已由用户明确；具体技术底座待 M0 验证。

## 背景

用户创建了 autoscientists-engineering 仓库，并指定 D 盘工作区。最初调研集中在 AutoScientists 及其工程化。

用户进一步明确：“就是探索性的任务，我不想把这个模式局限的太死，任务可以宽泛一点，就是开放性问题之类的”。

因此，数值优化、标准科研实验或论文生产不能作为通用任务入口。

## 决定

1. 用可修订的问题地图、研究动作、发现与证据组织探索。
2. 下一步由当前问题和发现决定，不规定每个任务必须按同一阶段顺序推进。
3. 允许多种解释、创意、反例、未知与阶段性结果。
4. 将模型适配、工具、执行状态与项目记忆分开。
5. 先评估通用代理底座，优先复用代理运行与恢复机制。
6. 单代理完成可用闭环后，再评估多视角与动态协作。
7. 代码、分析、原型、实验和论文输出作为按需能力。
8. 默认本地单用户；早期 CLI 验证，工作流稳定后增加 Web 工作台。

## 候选及取舍

| 路线 | 优点 | 需要验证的成本 |
| --- | --- | --- |
| 基于 DeerFlow 扩展 | 已有通用工具、记忆与交互结构 | 部署依赖、扩展点、与项目知识模型的匹配 |
| 基于 Deep Agents 做薄产品层 | 通用代理能力可组合，产品层可控 | 交互和项目对象仍要实现 |
| 封装现有编码代理 | 可以快速复用工具和文件操作 | 结构化状态、稳定接口、长期运行管理 |
| 直接围绕 AutoScientists 改造 | 适合实验研究及方向协作 | 容易把产品过早绑定到可量化任务 |
| 独立自建完整框架 | 边界完全可控 | 会重复开发上下文、工具、状态和模型适配 |

优先验证前两条，保留轻量封装作为成本对照。最终采用哪条路线需另写 ADR，不以本提案代替实测选型。

## 对用户的影响

用户可以从一句宽泛问题开始。系统可先选几个暂定角度推进，而不要求先补齐完整计划和指标。

用户得到一个可持续的探索项目，而不仅是一份最终报告。没有确定答案时仍可留下有用的认识、分歧和下一步。

## 对工程的影响

原版 AutoScientists、OpenResearch 和实验调度设计移到可选集成范围。记录与恢复仍重要，但首个演示改为固定资料包上的开放问题探索，不以训练分数作为验收。

需要区分研究质量和执行正确性：模拟代理可测恢复与记录，真实模型和资料才可评估探索质量。

## 重新评估条件

- 首批使用发现主需求实际偏向模型/代码实验。
- 通用底座的部署或升级成本显著超过轻量方案。
- 用户需要多人协作或持续远程运行。
- 多代理在相同预算下表现出稳定收益。
