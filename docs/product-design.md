# 产品设计：开放问题探索工作台

状态：提案 v0.1。2026-10-24。

## 1. 已确认需求与假设

用户已明确：核心是探索性任务，可以是宽泛的开放问题，不希望把模式限定得太死。

用户已指定 D 盘工作区和 GitHub 仓库。除此之外，模型、预算、自动运行时长、部署方式和通知频率均未确认。

《日常探索模式》的正文尚不可读，不编造其中的设定。当前设计直接依据本次确认的开放探索需求。

## 2. 产品定位

帮助个人长期探索一个问题的研究伙伴与工作台。

系统应能面对不完整的问题，主动提出值得看的角度，查资料、比较解释、做分析或原型，把认识和未知留下来。用户能打断、引导、质疑，也能让它在给定范围内继续。

报告是阶段产物。项目本身包含尚未完成的方向、矛盾、失败尝试和待追问事项。

## 3. 什么样的任务应该接得住

| 示例 | 可能采取的行动 | 合理的阶段产物 |
| --- | --- | --- |
| 为什么很多自主代理演示很好，长期使用却不稳定？ | 分解原因、读实现和案例、寻找反例、设计小验证 | 原因地图、证据、尚有争议的解释 |
| 个人知识系统有没有比文件夹更好的组织方式？ | 比较方案、分析使用情境、尝试界面或小原型 | 概念模型、方案取舍、原型与新问题 |
| 小团队怎样更有效地形成研究想法？ | 连接不同领域观点、构造案例、推演机制 | 多种机制假设和可尝试方法 |
| 这两类看似无关的机制有没有共同结构？ | 类比、形式化、找差异、查相关工作 | 类比的有效范围、反例和候选研究方向 |

不要求用户先填写领域分类、标准数据集、评价指标或论文模板。系统可以先行动，再在需要时问具体问题。

## 4. 核心循环

    理解当前问题与用户关注点
        ↓
    建立或修订暂定问题地图
        ↓
    选择少量值得推进的方向
        ↓
    查资料 / 推理 / 比较 / 分析 / 原型 / 可选实验
        ↓
    保存发现、来源、论证、反例和新问题
        ↓
    回看原问题：继续、转向、合并、暂存或阶段总结

这是可反复进入的循环，不是固定 DAG。允许跳过某个动作、回到上一步，或重述原问题。

宽泛问题会有一个暂定的理解和行动范围，但无需先把问题收窄成不可更改的目标。

## 5. 三个推进尺度

| 尺度 | 用户体验 | 结束条件 |
| --- | --- | --- |
| 一步探索 | “先从这个角度看看” | 一个可解释的研究动作结束 |
| 一轮探索 | “围绕这个问题推进一轮” | 预算耗尽或得到足以阶段汇报的新认识 |
| 持续课题 | “这个问题以后接着研究” | 可跨多轮积累，用户决定何时归档 |

默认完成一轮后汇报。用户明确允许持续推进时，可在保存的预算和工具范围内继续。任务开放不等于无限循环。

“日常探索”可以是用户每天打开项目继续，也可以以后增加定时推进；本次不创建自动化或后台计划。

## 6. 问题地图

问题地图是可演化的关系网，初期用列表和关联链接即可表达。

节点可以是问题、概念、方向、解释、发现或待验证猜想。关系可以是“细化”“相关”“支持”“反驳”“依赖”“取代”。

- 同时保留多种解释，不强迫过早收敛。
- 新资料可以推翻旧解释；旧记录保留并标注变化。
- 无结果的方向可以暂存，环境或认识改变后再打开。
- 创意允许先存在，再标注哪些部分仅是构想。
- 不把搜到更多页面自动视为研究进展。

图结构在第一版可存入关系数据库，不为展示问题地图先引入图数据库。

## 7. 用户看到什么

建议最终界面是“项目对话 + 当前认识 + 可展开的研究记录”。

    当前项目：宽泛的探索问题                     [暂停] [继续]
    ┌ 项目列表 ┐  ┌ 当前认识与下一步 ┐  ┌ 项目对话 ┐
    │ 问题地图 │  │ 主要方向         │  │ 追问      │
    │ 资料     │  │ 新发现与分歧     │  │ 改方向    │
    │ 发现     │  │ 还不知道什么     │  │ 指定材料  │
    │ 活动     │  │ 建议的下一步     │  │ 质疑结论  │
    │ 阶段总结 │  └ 证据与产物详情 ┘  └───────────┘

用户首先看到：目前知道什么、为什么这样想、哪些仍不确定、接下来值得探索什么。

无需理解代理角色和任务状态机就能使用。多代理数量、Token 明细等放在活动详情，需要时再看。

M1 先提供 CLI 和 Markdown/JSON 导出，M3 再实现本地 Web。首轮可以人工阅读导出的结果来评估探索质量。

## 8. 每轮简报

每轮探索的默认输出控制为可快速阅读的一页摘要，可展开细节：

1. 本轮实际推进了什么。
2. 哪些认识发生变化，依据是什么。
3. 有什么反例、冲突或不确定性。
4. 新出现的有价值问题。
5. 下一步的两个或三个方向及各自理由。
6. 实际使用的工具、资源和仍在运行的工作。

引用分为原始材料、二手概述和系统自己的推断。引用存在并不自动代表引用支持该结论。

## 9. 自主性与引导

系统可以提出下一步，并在用户已授权范围内采取行动，不必每个搜索和笔记都重新确认。

涉及新的付费资源、超出允许的工具或修改范围时，先保存状态并说明具体缺口。预算是执行边界，不是衡量问题价值的标准。

用户的明确改向指令优先于当前计划。已开始的动作绑定原问题版本，后续结果标明产生时的上下文，避免把旧方向结果混入新结论。

## 10. 什么算好的一轮探索

观察以下维度，不合成一个虚假的“科研质量总分”：

- 是否忠实回应用户关心的问题，又能提出有依据的新角度。
- 是否区分事实、解释、猜想、类比和创意。
- 是否有可追溯的来源或清楚的论证链。
- 是否主动检查反例和相互冲突的材料。
- 是否形成新的理解，而非堆砌摘要或反复搜索。
- 是否留下可继续的具体方向。
- 重启后是否仍能接续，并知道哪些认识只是暂定。

没有定论可以是诚实的结果；没有任何新信息也要明确说明。

## 11. 首版范围

包含：宽泛问题录入、可修订问题地图、一个研究代理、资料读取、行动记录、发现与来源关联、阶段简报、暂停与恢复。

后续扩展：联网检索、代码/数据分析、原型和实验工具、多视角代理、跨课题连接、定时推进。哪些工具进入真实首版由 M0 选型和可用配置决定。

暂缓：多人组织、自动投稿、大规模计算集群和自建通用代理平台。

## 12. 待确认但不阻塞设计的事项

- 第一批希望探索的真实问题。
- 可用模型、检索服务和每轮预算。
- 是否需要接入已有笔记或文献库。
- 用户希望何时收到进展，以及机器是否会持续开机。
