# 开发协作：双账号、多 worktree 与云端

状态：工作方式提案，2026-10-24。当前仓库只有设计稿，尚无依赖安装命令、应用或测试套件。

## 1. 当前建议

本地采用两个独立 Codex 实例，各自操作一个任务 worktree 和分支；GitHub 保存任务说明、提交和 PR；同一时刻由一个集成者处理共享接口与合并。

先让两个实例形成稳定交付循环，再增加并行数量。账号用于开发工具登录，分支按任务命名，账号不绑定永久角色。产品运行时的智能体数量是另一个设计维度，不等于开发账号数量。

本文不要求创建新聊天、启动其他账号或改变登录配置。以下目录和命令为待采用方案，本次未实际创建任务 worktree。

## 2. 三层隔离

| 层次 | 需要分开的内容 | 管理方式 |
| --- | --- | --- |
| Codex 客户端身份 | 登录、客户端配置、会话和工具授权 | 沿用各自已配置的实例，分别核对账号与项目目录 |
| Git 任务工作区 | 文件修改、HEAD 和暂存区 | 一个写任务一个 worktree、一个分支 |
| 应用运行环境 | 虚拟环境、数据库、输出、运行 ID、服务端口 | 各 worktree 独立配置与运行目录，服务使用不同端口 |

Git worktree 共用仓库的对象和分支等元数据，不是完整虚拟机。一个分支不能同时在两个 worktree 检出；共享仓库配置和分支维护由集成者协调。

Codex++ 同名项目存在多个。已查阅的 BigPizzaV3/CodexPlusPlus 作者 README 描述了独立实例的配置、会话和用户数据隔离；用户实际版本尚待确认。具体按钮与功能按所安装版本核对，本文的 Git 工作方式不依赖它的增强功能。

不通过复制整个客户端主目录来交接开发。把已完成内容写入 Git，把待办与验证写入任务说明，另一个实例即可基于同一提交继续。

当前主 checkout 仍位于 codex/open-exploration-design，设计草案在 PR #1，main 尚不是完整设计基线。本次不自动切换主 checkout 或合并该 PR。

## 4. 创建 worktree 的操作示例

下面的 PowerShell 命令用于设计稿已合并后的新任务。它们不属于当前已执行步骤；路径、分支名和基线需按实际状态选择。

```powershell
Set-Location 'D:\autoscientist\autoscientists-engineering'
git status --short --branch
git fetch origin

$exploreBase = (git rev-parse origin/main).Trim()
git show --stat --oneline $exploreBase

New-Item -ItemType Directory -Force -Path 'D:\autoscientist\worktrees'
git worktree add -b codex/m0-mechanism-map 'D:\autoscientist\worktrees\m0-mechanism-map' $exploreBase
git worktree add -b codex/m0-runtime-spike 'D:\autoscientist\worktrees\m0-runtime-spike' $exploreBase

git worktree list
```

在实例 A 中打开 mechanism-map 目录，在实例 B 中打开 runtime-spike 目录。每个写任务开始前检查 cwd、分支、HEAD 和状态；不能让两个会话同时写同一个 checkout。

已有分支或路径时先检查现状，不用 -B 或 --force 覆盖。清理完成任务时使用 Git worktree 管理命令；先核实已提交/推送和本地运行产物，不能因为 Git 状态干净就假设忽略目录没有要保留的数据。

Codex 原生也提供受管理 worktree。早期可选择手工固定目录，便于在两个客户端中准确打开；不要同时让不同管理方式创建同名任务。受管理 worktree 的生命周期和手工 worktree 分别管理。

## 5. 双账号怎样分工

建议开始阶段保持两个写任务；评审可以在写任务暂停后进行。谁负责集成由本轮明确，不要求某个账号永远只做规划。

| 阶段 | 实例 A | 实例 B | 汇合点 |
| --- | --- | --- | --- |
| M0 调研 | AutoScientists 调用链、共享状态及协议执行边界 | 候选执行接口、Windows 前提和小场景验证计划 | 共同形成机制映射和选型 ADR |
| 基础接口 | 最小对象、事件和适配器契约，先给出可审阅提交 | 依据草案准备独立材料包、故障情景和验收条目 | 接口提交确定后再并行写依赖代码 |
| M1 实现 | 一块明确的核心功能，例如共享记录与方向变更 | 一块边界清楚的功能，例如代理适配和固定材料工具 | 同一协议版本上的端到端验证 |
| 收尾 | 处理集成、发现的缺陷和文档 | 审查确定提交、复查验收结果和遗漏 | 一个 PR 完成定义满足后再合并 |

任务按依赖拆分。不要在没有共同接口提交时，让两个实例分别发明自己的 Post、Action、AgentState 和预算接口。

接口文件、依赖清单、锁文件、数据库迁移和 CI 配置在同一时间有一个明确修改者。另一个任务需要改动时，先把需求记录成明确变更，确认新的接口提交再继续；正常代码模块仍按各自分支并行。

## 6. 每个任务的最小交接卡

任务卡放在 GitHub Issue、PR 正文或仓库任务文档中，选择一处作为权威，不要求重复维护。

```text
任务：一个具体结果
基线：分支 + 完整 commit SHA
工作区：绝对路径
任务分支：codex/<task-name>
目标与边界：要交付什么、由谁拥有共享接口
输入：设计版本、相关接口提交、材料位置
允许修改：具体模块或文档
依赖：必须先完成/合并的提交或任务
验收：可执行检查、预期行为、失败路径
资源：允许的服务、工具、预算；默认离线测试
交付：commit/PR、实际检查结果、未解决问题
```

任务卡只列与本任务有关的约束。新的需求通过更新任务卡和提交版本同步；聊天可补充背景，不能是唯一交接记录。

## 7. 每次交付怎样进入主线

1. 从明确基线创建任务分支与 worktree，在独立目录完成改动。
2. 完成与改动相关的验证，提交代码并推送任务分支。
3. PR 描述具体行为、验收证据、依赖和仍有的限制。
4. 另一个实例针对固定 head SHA 检查设计与实现、失败路径及测试。修复仍回到原任务分支。
5. 集成者处理冲突，在最终准备合并的提交上完成相关检查，再合并。
6. 下一个依赖任务从已合并基线开始；仍在进行的任务由其拥有者更新基线。

评审可以阅读 GitHub diff，或在单独的 detached worktree 检出确定提交。评审者不在对方正在运行的目录里切分支、重置状态或修改文件。

对依赖较强的功能，先合并小接口 PR，再并行实现两侧。不要用复制未提交文件的方式把不同 worktree 拼起来。

本机 worktree 不会自动包含其他 worktree 未提交的修改；跨机器更需要推送提交后 fetch。发现问题时记录具体提交和可复现步骤，避免只说“另一个窗口已经改好了”。

## 8. 现在最合适的前两个任务

任务 A：源码与机制核对。

追踪 AutoScientists 的实际启动、唤醒、会话、共享读写、认领和重组，输出固定版本调用链，标明哪些是模型遵循的协议、哪些是程序强制约束。先只读分析，产出机制映射文档，不修改产品核心接口。

任务 B：运行接口与验收准备。

针对已讨论的最多两个候选，核实独立会话、结构化输出、并发、状态和 Windows 启动方式，设计三个参与者的小场景；准备本地材料包与失败情景。运行依赖、付费调用与外部服务按已授权范围处理，缺失条件明确标记。

两项完成后一起决定：具体复用哪个执行器，哪些共享协议需自己实现，以及第一个可运行切片的接口。首批核心代码不宜在选型与接口仍互相变化时大规模分头生成。

## 9. 云端有三种用途

| 用途 | 适合做什么 | 需要的条件 |
| --- | --- | --- |
| Codex Cloud 开发任务 | 独立代码改动、测试、文档和 PR 工作 | 该账号可访问的已发布环境、仓库权限、可复现工具与材料 |
| 自己的远程开发机 | 需要保留完整开发环境、进程和长期调试的工作 | 远端 clone、已配置的连接与独立开发环境 |
| ExploreOS 的服务部署 | 持续推进探索、保存项目状态、运行后台服务 | 本产品已经具备运行、权限、预算、持久化与恢复能力 |

云端开发任务和产品常驻服务分别设计。早期用云端改代码，不意味着已经解决产品无人值守运行。

官方文档说明，Codex Cloud 每个任务有独立文件状态，所用环境需要发布；本机文件、进程和浏览器登录不会自动进入云端。对远程开发机的 SSH/host handoff 也不能直接等同于迁移到 Codex Cloud。

两个客户端的 Cloud 可用性与环境/仓库访问权分别核对。Codex++ 多开和模型供应商配置本身不能证明某账号已具备所需的云端环境。

## 10. 什么时候可以开始云端开发

### 当前：可以先做仓库内的文档和只读调研

若账号已有可访问的 Cloud 环境，可提交范围清楚、依赖仅为仓库和公开材料的任务。当前仓库没有应用安装和测试入口，不能宣称云端已经能构建或验证产品。

本地未提交的设计、D 盘材料和只在本机启动的服务，必须先以合适方式提供或从任务中移除依赖。私有材料不因开发方便就加入公开仓库。

### 最早代码门槛：第一个可复现小切片完成后

无需等待整个 MVP。建议以下条件满足后，将独立模块、测试和评审交给 Cloud：

- 一个干净 clone 可以按已提交说明安装依赖，版本与锁文件已明确。
- 有小型固定材料包和确定性 Fake Agent，测试默认不调用付费模型。
- 明确安装、离线测试和最小示例命令，脚本不硬编码 D 盘。
- 模型后端、工具和路径均可配置，缺失配置会明确报错。
- Windows 本地检查和 Linux 检查的范围已说明。
- 任务已推送到明确基线，任务卡给出允许修改范围与验收。
- 该账号已配置所需的云端环境、网络和仓库访问，设置验证后已发布。

这些是本项目的推荐接入门槛，不是 Codex Cloud 的统一产品要求。相关脚本、测试和 CI 当前尚未实现。

### 多轮真实探索与常驻运行

真实模型、多工具联调仍优先在容易观察的环境验收。通过预算、失败、重启和产物核对后，再将持续探索放到适当服务器，单独配置存储、日志、模型后端和通知。

首版默认采用外部模型执行接口，本轮不采购服务器或 GPU。是否需要专用计算资源取决于后续加入的实际工具与实验。

## 11. 本地与云端怎样交接

交接内容为仓库、分支/commit、任务卡、测试材料、配置说明和验证命令。

云端完成后推送任务分支或交付 PR，本地 fetch 后按正常评审集成。原始运行材料和数据库有独立备份/导出路径，不把开发 PR 当作运行状态同步机制。

本机专有的技能、Codex++ 注入增强和桌面连接不列为云端任务的隐式依赖。云端需要的开发指令放在仓库中，凭据按环境配置提供，不能从本机复制整个登录目录。

Linux Cloud 的通过结果不替代 Windows 路径、子进程和退出行为检查。后续 CI 建议覆盖两种平台上的离线核心测试，真实付费探索采用明确配置的独立运行。
